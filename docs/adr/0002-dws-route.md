# 0002. 千问×钉钉接入采用 dws 官方路线，社区全链路平台作兜底

- 状态：已接受
- 日期：2026-11
- 相关：ADR-0001（暂缓技术栈选型）、docs/tech-scan.md（选型调研）

## 背景

需求已明确：打通千问与钉钉，围绕群消息读取、文件识别、知识库、工作台，
以群数据为底座。选型依据见 docs/tech-scan.md（每项结论附核实级别）。

关键事实：群历史全量消息无传统开放 API，但官方 dws 能以登录用户身份
实时订阅全部群消息并覆盖 wiki/drive/aitable/doc 等服务面，前提是
企业管理员授权。**企业授权已确认可得（2026-11-20）**，此前唯一的
可行性疑问消除，本 ADR 据此成立。

## 决策

我们决定：接入层以官方 `dws`（DingTalk-Real-AI/dingtalk-workspace-cli）为主路线，
千问（DashScope / Qwen Code）作为驱动 dws 的模型层；
文件识别用 MinerU 或 RAGFlow，知识库底座用 RAGFlow + `dws wiki` 同步；
机器人回写群消息用官方 dingtalk-channel-sdk，或 CowAgent/LangBot 兜底。

明确不做的：不采用灰色方案（桌面 hook、手机转发）作为生产路径；
不在没有需求的情况下引入 CI 与构建配置（沿用 ADR-0001）。

## 考虑过的方案

| 方案 | 优点 | 缺点 | 放弃原因 |
|------|------|------|----------|
| dws 官方路线（采纳） | 全量群消息订阅、wiki/drive/aitable 官方支持面、零自研接入 | 需企业管理员授权；Co-creation 阶段，部分事件投递未验证 | 无——前提已满足 |
| CowAgent/LangBot 自托管全链路 | 部署即用、自带网页后台；模型可切千问 | 只收 @机器人消息，无全量订阅 | 作为兜底保留，不作主路线 |
| 灰色方案（桌面 hook / 手机转发） | 唯一能拿历史全量的路径 | 封号与合规风险 | 明确排除，不进生产 |

## 影响

- 正面：群消息读取从"只收 @消息"升级为"全部消息实时流"；知识库、文件、
  工作台都有官方 API 面，自研量最小。
- 代价 / 风险：dws 处于 Co-creation 阶段，事件投递的 production readiness
  官方未完全验证，上线前须实测；企业授权凭据的保管责任在授权方（本仓库侧
  沙箱环境为临时环境，凭据随会话失效）。
- 需要一并改动的东西：tech-scan.md 的遗留决策点已更新；
  工作台形态（aitable 仪表盘 vs 自建网页后台）仍待定，落地时另立决策。

## 如何验证这个决定是对的

- 观察信号：dws 授权后 `event consume` 在目标群稳定收到非 @消息；
  `wiki`/`drive`/`aitable` 命令在企业环境实际可用。
- 复核时间：首次端到端连通测试后立即复核；若授权范围或事件投递
  与文档不符，按 ADR-0001 的失效条件重新选型（社区路线兜底）。
