# 0001. 暂缓技术栈选型，仓库先只放约定与文档

- 状态：已接受
- 日期：2026-11
- 相关：无

## 背景

仓库建好后是空的，描述为"软件开发专用"，但具体要开发什么尚未确定。
在没有需求的情况下引入 `package.json` 或 `pyproject.toml`、CI 配置和测试脚手架，
得到的是一套无人验证过的配置：依赖版本会随时间陈旧，CI 会在第一次真正写代码时
暴露出从未运行过的问题，而它看起来已经"准备好了"。这种空的工程骨架比没有骨架
更容易误导后续判断。

前提：这个仓库确实还没有确定的第一个功能目标。如果这个前提失效（已经有明确要做
的东西），本 ADR 立即作废，直接按需求选型。

## 决策

我们决定：**暂不引入任何语言依赖、构建配置和 CI**，仓库只保留目录约定、协作规则和
文档骨架。选定技术栈时另写一条 ADR 取代本条。

明确不做的：不预装 lint/format 工具链，不加 GitHub Actions 工作流，不建虚拟环境
或 lockfile。

## 考虑过的方案

| 方案 | 优点 | 缺点 | 放弃原因 |
|------|------|------|----------|
| 现在就选 Node/TypeScript | 立刻有可用的构建与测试基线 | 需求未定，选型没有依据 | 等于凭偏好做架构决定 |
| 现在就选 Python | 同上，脚本类任务起步快 | 同上 | 同上 |
| 同时放两套脚手架 | 之后无论选哪个都有底 | 双份维护成本，且传递"什么都行"的错误信号 | 没有任何场景需要它 |
| 只放约定与文档（采纳） | 不产生未经检验的配置；选型时信息更充分 | 首次写代码前要再做一轮基建 | 成本延后而不是消失，且延后期正好用来收集需求 |

## 影响

- 正面：不会出现"配置就绪但从未跑过"的假状态；选型决策会留下一条有依据的 ADR。
- 代价 / 风险：第一个功能落地时要先补一轮工程基建，短期内没有 lint / CI 兜底。
- 需要一并改动的东西：选定技术栈后，README 的"目录结构"一节要补实际入口与运行命令；
  届时新增 `.github/workflows/`，并把本条 ADR 标为"已取代"。

## 如何验证这个决定是对的

- 观察信号：如果在本条生效期间出现"急着加依赖但没有需求支撑"的提交，说明暂缓没有执行到位。
- 复核时间：下一次有具体功能要做时立即复核，最迟不超过第一次有人往 `src/` 放代码之前。
